# 24 — ANTIGRAVITY PROJECT CONSTITUTION

Read this before implementing or modifying CARDVERSE.

## Product

CARDVERSE is a browser-first idle collectible card game.

Core fantasy:

**Build a collection that builds itself.**

Core loop:

**CLICK / IDLE → COINS → PACKS → CARDS → SETS → IDLE INCOME → MORE PACKS**

## Absolute rules

1. PvP does not exist in CARDVERSE.
2. Do not introduce combat unless explicitly approved as a future product decision.
3. No NFTs/blockchain.
4. No paid randomized Packs in MVP.
5. Donations must not grant randomized card purchases.
6. External APIs are content sources, not gameplay authority.
7. Never require an external API during a Pack opening.
8. Never expose privileged provider keys in frontend code.
9. Never assume an API image is licensed for our intended use.
10. Never use provider IDs as the only canonical content identity.
11. Never break old local saves; add migrations.
12. Do not add new universes by copying existing universe-specific logic. Use provider/content abstractions.
13. Do not make clicking the permanent main activity. Clicking is the early economic engine; idle and collection should take over.
14. Do not make completed Sets meaningless. Set completion is a core economic milestone.
15. Never create a quest that requires an unavailable prerequisite resource during onboarding.
16. Do not make the player buy Packs with real money in MVP.
17. Do not create artificial scarcity merely to inflate engagement. Scarcity must serve collection design.

## First-time player flow

The first session must follow this conceptual sequence:

START
→ free Beginner Discovery Pack
→ open 5 cards
→ Collection
→ second Pack opportunity
→ clicker introduction
→ earn Coins
→ third Pack
→ duplicate → Essence
→ first upgrade
→ Sets
→ first passive income
→ player level/quests
→ free exploration

The exact implementation may evolve, but the player must understand the economic loop before being asked to grind.

## Domain boundaries

### Content
External-world facts.

### Card
CARDVERSE collectible representation.

### PlayerCard
Ownership.

### Set
Designed collection.

### Rarity
CARDVERSE property.

### Pack
Reward generation configuration.

### Economy
Coins/Essence/Tickets.

### Idle
Click, automation, Set production, offline income.

### Provider
External data source.

Do not mix these.

## Economy principles

Coins:
- main free resource;
- earned actively and passively;
- spent on Packs and upgrades.

Essence:
- primarily duplicate sink;
- spent on upgrades/mastery.

Pack Tickets:
- quest/achievement/event reward;
- can open selected Packs.

No premium currency in MVP.

## Idle progression

Early:
- clicking matters.

Middle:
- click upgrades + automation matter.

Late:
- completed Sets become major income sources.

Offline income is capped.

The intended player experience is to transition from active clicking to collection management.

## Set production

Completed Sets generate passive Coins.

Example:

Set completed:
+10 Coins/sec

Set mastered:
+20 Coins/sec

Exact numbers are balance configuration, not hard-coded assumptions.

## Code quality

- TypeScript strict.
- Pure game logic separated from React.
- Tests for economy and pack math.
- Stable IDs.
- Versioned saves.
- Graceful provider failure.
- No duplicated business logic.

## Required tests

### Click
Given click power, result is deterministic.

### Idle
Income/sec calculation is deterministic.

### Offline
Offline earnings never exceed configured cap.

### Pack
Configured rarity distribution is respected.

### Collection
Duplicate increases quantity but not unique count.

### Set
Completion activates production exactly once.

### Upgrade
Insufficient Essence/duplicates cannot upgrade.

### Save
Old schemas migrate.

### Provider
Malformed records do not crash ingestion.

## Feature Definition of Done

A feature is complete only when:

1. It fits collection-first design.
2. It does not introduce PvP.
3. It respects domain boundaries.
4. It works on mobile browser.
5. Persistence behavior is defined.
6. Error states exist.
7. Critical logic has tests.
8. Secrets are protected.
9. Content rights are considered.
10. Documentation is updated.

## AI workflow

Before a major change:

1. Read relevant documentation.
2. Inspect existing code.
3. Identify the correct domain module.
4. Reuse existing abstractions.
5. Implement the smallest coherent change.
6. Test critical logic.
7. Update documentation.
8. Explain architectural deviations.

Do not rewrite working systems merely for style.

## Decision hierarchy
